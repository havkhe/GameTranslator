GameTranslator v2.4 — 修复续翻/已汉化误判，防卡死，支持无 www 的 MZ 布局
=====================================================================

本版是 v2.3.2 之后的正式修复版，只改“正确性与稳定性”，不引入新依赖。
（v2.4 开发过程中分两批提交：正确性修复 + 稳定性/防卡死。）

〇、第二批：防卡死与请求层加固
------------------------------
  · 修复“软件像卡住”的根因：模型陷入退化复读时，旧版只断开客户端 socket，
    服务端的生成仍在继续，后续重试排队堵在同一个槽位上，表现为整机假死。
    现在：
      - 请求超过 45 秒没有任何新数据即判定 STALL_ABORT，主动断开并请求
        llama-server 清空槽位（POST /slots/N?action=erase）；
      - 连续 3 次卡死即判定 MODEL_DEGRADED，停止本次运行（进度全部保留、
        待翻译条目写入 failures.json），而不是无休止重试；
      - 实测：卡死场景从“>104 秒仍未结束”变为“12 秒内干净退出”。
  · max_tokens 按输入长度收敛（约 源字符×2 + 32/行，上限 1024）。
    旧版固定 2048，等于给复读留了 2000 token 的空间；现在从物理上掐断。
  · 采样参数与服务端一致并对齐模型作者推荐：
      temperature 0.3 / top_p 0.8 / frequency_penalty 0.1；
      llama-server 启动参数同步加 --temp/--top-p，并默认开启 --metrics。
  · 请求改为带官方 system 提示词（“你是一个轻小说翻译模型……不擅自添加
    原文中没有的代词。”），与模型训练格式一致。
  · 默认提示词改为“逐行输出、不编号、不要JSON”；**旧版保存的 JSON 提示词会
    被自动升级**（GUI 设置项与 pipeline 各做一次识别，手写提示词不被动）。
  · 请求失败不再静默：首次请求异常会打印 REQUEST_FAILED，便于定位“服务没起来”。
  · 工具提示：出现 MODEL_DEGRADED 时，重新点“开始汉化”即可从断点继续；
    若反复出现，可在“llama 高级设置”里降低批大小或换更小模型。

一、最严重的问题：重复汉化同一游戏会“越翻越乱”
------------------------------------------------
旧版在重新运行时会从**已经被汉化过**的数据文件里重新抽取“原文”，于是：
  1) 译文缓存完全命中不上（缓存用抽取下标作键，抽取源一变全部错位）；
  2) 已翻译的几千条被当成待翻译，整局重翻；
  3) 更糟的是把自己的中文再翻一遍（"把中文翻译成中文"），
     每跑一次游戏文本就被包一层，逐渐不可读。

v2.4 的修法：
  · 翻译源改为 data_原版备份（原始日文）；活动目录只用于补充"备份之后新增的内容"；
  · 译文缓存改为按**原文文本**存储，并对活动目录的文本做双重过滤
    （已像中文的、以及等于历史译文的，一律不再送翻译）；
  · 旧版按 id 存储的缓存在首次运行时自动迁移，历史进度不丢。

实测（合成数据 + 真实游戏）：
  第一次：TOTAL 9 PENDING 9 → 1 次请求 → 完成
  第二次：TOTAL 9 DONE 9 PENDING 0 REQUESTS 0（完全命中，零请求）
  第三次、第四次：同上，游戏文本保持不变（幂等）

二、其它正确性修复
------------------
  · 超长单条文本按标点切段翻译后拼回，不会因一条长文本撑爆上下文而拖垮整批；
  · 整批失败改为对半拆批重试（16→8→4→…→单条），单条再失败则记入
    failures.json 并在下次自动重试；失败记录按原文哈希去重，
    修掉旧版"批次下标错位"造成的虚假失败；
  · 新增 work\<游戏>-patch-report.json / -translate-report.json：
    回写替换数、未匹配数、请求数、拆批次数、失败数，回写异常不再静默；
  · 引擎识别支持"无 www 目录"的 NW.js 打包 MV/MZ（data 与 js 与 Game.exe 同级）；
  · “已汉化(跳过)”不再仅凭 data_原版备份 存在与否判断
    （旧版会把"还原过原版"的游戏永久跳过）；VX Ace 不再按文本统计二进制数据；
  · 说话人名字（指令 101）纳入抽取；355/405/655 脚本指令仍然绝不翻译；
  · 每批落盘并输出进度，终止最多丢 1 批；还原 bat 兼容 www\data 与根目录 data\；
  · MV 侧补上条目长度保护（VX Ace 侧原本已有）。

三、兼容性
----------
  · 旧 work\*-translations.json（id 键）首次运行自动迁移，无需手动删除；
  · 旧 work\*-untranslated.json 仍会被用于"检查翻译后重翻"；
  · settings.json、模型、llama 运行参数完全不变，无需改动用户配置；
  · VX Ace 侧 vxace_extract.rb 未改动，vxace_patch.rb 兼容两种缓存格式。

四、验证方式（本版实测）
------------------------
  · 端到端测试 **45 项全部通过**（合成 MZ 游戏 + 假 llama 服务，不占 GPU）：
    引擎识别/抽取取舍/回写/备份/还原脚本/缓存迁移/续翻零请求/检查模式/
    失败降级/失败恢复/幂等性/请求参数（采样与 max_tokens 收敛）/提示词升级/
    卡死中止与槽位清理；
  · 真实 VX Ace 数据（49 个 rvdata2、2533 条）：新旧两种缓存回写
    均替换 710 条、0 错误，重新抽取仍是 2533 条（Marshal 往返完好）；
  · 真实 MZ 游戏：以前完全识别不出的《Stealing My Brother's Wife》
    现在能正常识别与抽取；《The Impure Lewd Flower》抽取 1092 条；
  · 真实日文质量对照（14 条真实台词，同一批上下文）：
    旧 JSON 提示词与新默认逐行提示词均 0 缺行、0 假名残留，
    译文长度 203 vs 204 字，新默认在断句/用词上略有改善；
  · 性能实测（GTX 1060 6GB / Galtransl-4B）：解码 ≈37.2 token/s，
    提示词格式、system 消息、-np(1/2/4)、--cache-reuse 对吞吐**均无影响**，
    即当前硬件已到天花板；不要指望调这些参数提速。

五、性能结论（重要，避免走弯路）
--------------------------------
  · 单条耗时 ≈ 输出 token / 37.2 + 固定开销，实测约 0.4 秒/条（短台词），
    输出 token 数由译文本身决定（16 行 ≈129 token）；JSON 脚手架并没有
    额外浪费，换提示词格式**不提速**；
  · 因此提速只有三条路：换更小/更快的模型、投机解码
    （--model-draft 同系列小模型）、或让模型少生成（更短译文）；
  · 真正值得投入的是“不卡死 + 不重翻”，这两项本版已完成。

六、仍未处理（留待后续版本）
----------------------------

  · 投机解码、vxace 归档重打包的位运算加速、Shift-JIS 文件名。

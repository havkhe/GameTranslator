## 一、结论

| 项 | 数值 |
|---|---|
| 剩余待译 | **336,137 条 / 6,678,521 字**（76 局） |
| 预估输入 token | ≈ **14.1M**（占大头：原文 + 每请求重发的指令） |
| 预估输出 token | ≈ **3.8M**（中文译文） |
| **合计** | **≈ 17.9M tokens**（不确定区间 **15.5M – 21.0M**） |
| 每局平均 | ≈ 23.6 万 tokens |
| **1M 免费额度能翻多少** | **≈ 37 万字 ≈ 4 局**（余量的 6%） |

**所以：按"每个模型 100 万免费额度"算，免费额度翻不完现在这批剩余工作。**
整批要 **≈ 18 个模型额度**（链上凑够 18 个模型，或部分改成付费/用本机模型补）。
反过来，如果只想先把**某几局**翻掉：一局几万到一百多万不等，最大的那局（`_OreNo小屋…`）单独约 **1.8M**。

## 二、怎么算的（哪些是实测、哪些是假设）

**实测（直接量自你机器上的产物）**：

| 项 | 数值 | 来源 |
|---|---|---|
| 中文长度 ÷ 日文长度 | **0.82** | 16.7 万条已完成译文与其原文逐条相除 |
| 平均每请求条数 | **4.4** | 这批实际发出的 38,370 次请求 / 167,360 条（批量已生效） |
| 原文/译文总字数 | 289.9 万字 → 237.8 万字 | 同上 |

**假设（明确写出来，供你替换成实测值）**：

| 项 | 取值 | 区间 | 依据 |
|---|---|---|---|
| 日文原文 → token | 1.0 /字 | 0.8 – 1.3 | Qwen 系分词器对假名/汉字大致一字一 token |
| 中文译文 → token | 0.7 /字 | 0.5 – 0.9 | 中文词表会合并常用词，比日文便宜 |
| 每请求指令块 + system | 300 token | — | 每次请求都要重发（批量越大摊得越薄） |

公式：
```
输入 = 原文总字数 × 1.0 + 请求次数 × 300
输出 = 原文总字数 × 0.82 × 0.7
```
注意 **输入占大头**：原文本身要送一遍，指令又随每个请求重发一次。所以**批量越大越省**——
平均每请求 4.4 条时，指令摊到每条约 68 token；若退化成一条一请求，这部分会翻 4 倍多。

## 三、用真实用量取代推算（已完成）

云端模式下，`pipeline/translate/client.js` 会把接口返回的 `usage` 累加（prompt / completion / total，
以及请求次数），一局跑完：

- 日志里出现一行：`API_USAGE prompt 1234 completion 567 total 1801 (5 次请求，云端接口上报的真实用量)`
- 该局的 `work\<局>-translate-report.json` 里多出一个 `apiUsage` 字段（本地模型模式全为 0）。

也就是说：**你随便挑一局先跑，就能把上面那张"假设表"换成实测值**，再乘剩余字数即可精确估算额度够不够。
单测 `tools/unit-api-mode.js` 覆盖了这段累加（25 项断言全过；合计 16 个套件全绿）。

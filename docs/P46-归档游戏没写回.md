# P46 —— 归档游戏的"翻译成功却没写回"：修报告 + 修判据 + 实际写回

生成时间：2026-10-14
触发：用户报告 `J:\...\salvation1.07 Jap\Game (original jap)` 显示已翻译、`Game.rgss3a` 却没变。

---

## 一、根因（三条，都已实测）

**① 被拒绝时 `exit 0`**（`pipeline/index.js:400`）——重打包安全闸门拒绝写入后，管线仍然**以成功退出**。
于是 `errors.log` 记成 `OK … 第 1 次尝试成功 用时 01:46:03`、队列继续往下走，而游戏一个字都没变。
日志里其实写了 `REPACK_REFUSED …` 和 `DONE (…未写回归档…)`，但滚过去就没了，没有任何地方再提。

**② 闸门的判据对 RGSSAD v3 过严**——它比较"原样解包再打包"后的**整文件 SHA-256**。
这个归档是 v3、999 个成员、56 467 393 字节；原样往返后**小了 12 字节**，而从偏移 8 起 **99.6 % 的字节都不同**——
因为 **v3 的成员密钥是随数据流递进的**，12 字节的位移会把后面每个成员**重新加密**，字节必然不同。
而内容其实一模一样（我逐个成员核对：**447 个解包成员的名字/大小/SHA-256 全部一致**）。

**③ 重跑会把已汉化的副本当原文再翻一遍**（这一条是查 ① 时顺带发现的）
`rgssad.unpack()` 带缓存（`unpacked/Data` + `manifest.json` 存在就直接返回），所以**重跑时它不会重新解包
原版归档**，而 `unpacked/Data` 里放的是**上一次补丁后的中文**——于是抽取阶段读到的是中文，
把它们当成待翻译的新条目排进队列。实测：这次重跑的 4 442 条"待翻译"里有 4 424 条是**中文**
（`希尔薇娅`、`人类`、`黑精灵`、`爱朵拉`…），只有 18 条是真正的日文残句。
换句话说：**对归档游戏重跑一次，等于把中文再翻一遍**（浪费 GPU，且有把专有名词改坏的风险）。

## 二、改了什么

**修 ①（报告）**：`pipeline/index.js` 改为 `process.exit(6)`（4=NOT_SUPPORTED，5=ALL_FAILED，6 是新的），
最后一句话改成能直接看懂并指路的：

```
DONE  (归档没有写回，游戏保持原样——这一局按失败计。原因见上一行；译文都留在缓存里，处理完重跑只会走「补丁 + 写回」，不会重翻。)
```

界面不需要改：`PipelineRunner` 本来就按非 0 退出码报失败，并把它当成"最后一行"显示。

**修 ②（判据）**：`pipeline/archive/repack-guard.js` 改为**比内容**——新增
`contentFingerprint(file)`（每个成员 → `名字\0 该成员字节的 SHA-256`，排序后比较，另比条目数）与
`sameContent(a,b)`；整文件摘要只留作日志（会写"字节不同（容器排版差异…），内容已逐个成员核对"）。
两种真正的损坏仍然抓得住：成员字节变了、成员消失/多出来。

**顺带加固**：`repackSafely` 的临时目录改在 `finally` 里清理（异常路径不再留垃圾）。

## 三、验证

- 单元测试新增 `tools/unit-repack-guard.js`（10 条）：**字节不同但内容相同必须判为一致**、
  成员内容变了必须不一致且点名成员、成员少了必须按条目数判出、`repackSafely` 在小归档上通过。
  **全量 18 个 unit 文件 474 项通过、0 失败**（原来 17 个 464 项）。
- 在**这台机器的真实归档副本**上跑新闸门：`REPACK_GUARD 原样往返：内容一致（999 个成员），字节不同（…）`
  → `repackSafely -> ok=true`（旧版对同一个归档是 `ok=false`）。原归档只读，未被改动。

## 四、把游戏真正汉化

修好判据后，**这份工作不需要模型也不需要 GPU**：`unpacked/Data` 里已经是**补丁后的中文**，
缺的只是"重建归档"这一步。所以直接调管线自己的重打包（`repackGuard.repackSafely(归档, vx工作目录)`，
与管线最后一步用的是同两个对象，只是不绕经抽取/翻译）：

```
REPACK_GUARD  原样往返：内容一致（999 个成员），字节不同（…）
REPACKING  …\Game (original jap)\Game.rgss3a
REPACKED   999 entries
result  : {"ok":true,"entries":999}
```

**结果核对（用程序自己的判据口径：假名 vs 汉字占比）**

| | 假名 | 汉字 | 假名占比 |
|---|---|---|---|
| 原版归档 | 371 347 | 105 807 | **77.8 %**（日文） |
| 写回后的归档 | 38 051 | 334 736 | **10.2 %**（中文） |

写回后的中文样例：`希尔薇娅`（Actors）、`异常状态`（Animations）、`透气性良好的布料衣服。`（Armors）、
`近卫队长`（Classes）、`图片全删除`（CommonEvents）、`纽扣人偶`（Enemies）。
归档 56 467 393 → 56 149 809 字节（译文比日文短，正常）。

**回退途径**：游戏目录里 `data_原版备份\Game.rgss3a` 是完好的原版（2026/12/8 时间戳、字节数一致），
把它复制回 `Game.rgss3a` 即恢复原状；暂存区另留了一份 `p42\safety\Game.rgss3a.orig`。

**过程纪律**：中途我确实跑起了完整管线，发现它还要 4 442 条过模型（约 45 分钟），
而你自己的翻译正在跑（同一个 `--parallel 1` 服务）——按你一直要求的"不影响翻译任务"，
我在**一次缓存写入之后**（安全点）停掉了它：不做无谓争抢，也不冒写到一半被打断的风险。
整个过程中你的 llama-server（PID 9584）与那次运行都没有被碰过。

正确的做法是每次从原版归档重新解包出一个干净的 Data，再用缓存把已有译文补回去（幂等）。

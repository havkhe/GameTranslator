## 一、结论摘要

| 问题 | 答案 |
|---|---|
| 长句是不是失败主因？ | **不是。** 1.8B 在 400+ 字桶 **3/3 全过**；通过率随长度**没有单调下降**（60-99 6/10、100-199 7/10、400+ 3/3） |
| 0.8B 为什么一条都没译出？ | **不是长度问题，是模型类型问题**：它先思考后作答，答案全在 `reasoning_content` 里，`content` 为空 → 管线报 `llama returned no content`。已修（见第四节） |
| 修好之后 0.8B 能用吗？ | **当作主力不建议。** 从 0/24 变成 9/24，但失败几乎全是 `unchanged`（**把原文原样吐回来**）——这是真实的"不听指令"，不是管线缺陷 |
| 用户看到的"部分长句译不出"是什么？ | **是质量闸门把合法字符当乱码**：`❤︎` 里的 U+FE0E 被列入"乱码特征"，一条里出现 ≥3 次即判死。全语料 **8,394 条（1.93%）** 命中，集中在少数几个游戏 |
| 能解决吗？ | **能，且是确定性的、不用换模型、不用重跑模型**：把 U+FE0E 从乱码字符类里去掉即可（见第七节） |

## 四、0.8B 一条都没译出：它是推理模型

`0.8B 改前` 最刺眼的数字是 **"成功请求 0"** —— 23 次拆分说明每一次请求都在报错，管线一路降级重试，全部失败。错误是管线自己的：

```
request-failed   REQUEST_FAILED "llama returned no content"
```

探针（`why-empty.js`，直接打 `/v1/chat/completions`）抓到根因：

| 请求 | `content` | `reasoning_content` | `finish_reason` |
|---|---|---|---|
| 原样（max_tokens 1024） | **空** | 3,492 字 | `length` |
| 原样（max_tokens 4096） | **空** | 16,732 字 | `length` |
| 带 `chat_template_kwargs:{enable_thinking:false}` | `"早上好，先生。"` | — | `stop`（5 token） |

也就是说：**它在"想"，答案一个字节都没进 `content`**。max_tokens 给到 4096，思考过程就写满 4096，正文永远轮不到。在提示词里写 `/no_think` **无效**（Qwen3 系列只认模板变量，不认提示词里的开关）。

**修复**（`pipeline/translate/client.js`）：请求体加 `chat_template_kwargs: { enable_thinking: false }`，默认开启，可用环境变量 `GT_NO_THINK=0` 关掉；同时把这种空回复的报错文案改成能自解释的一句：

> `thinking-only reply: N chars of reasoning_content and no answer（该模型先思考后作答，思考占满了输出预算；关闭思考后即可）`

效果：0/24 → **9/24**；单条从"3,492 字思考 + 空答案"变成"5 个 token 的正确译文"。**但这只是让它肯开口**，见第六节。

## 五、1.8B 的 16 → 13 是采样噪声，不是回归

`enable_thinking` 这个参数对 1.8B **本来是惰性的**，已直接验证：

```
$ GET /props  →  model_path: H:\model\Hy-MT2-1.8B-Q8_0.gguf
   chat_template 长度 596，其中是否出现 enable_thinking: 否
```

模板里没有这个变量，服务端收下即忽略 → 改前改后**行为不可能不同**。13 vs 16 的差落在 `100-199`（7→5）与 `400+`（3→2）两桶，**失败类型完全一样**（stray-chars / unchanged / control+code-invented / request-failed），温度 0.3 下的正常抖动。判定：**无回归**。

## 六、真正的剩余缺陷：闸门把 U+FE0E 当乱码

`pipeline/translate/quality.js:224`：

```js
const stray = d.match(/[―︎�]|ＥＮＤＩ|ＨＡＰＰＹ/g);   // 注：字符类里第二、三个是 U+2015 与 U+FE0E
if (stray) {
  if (stray.length >= 3) fatal.push("stray-chars:" + ...);   // ≥3 次 → 判死
```

三个字符里，`�`(U+FFFD) 和 `ＥＮＤＩ`/`ＨＡＰＰＹ` 确实是乱码 / 泄漏标记；但 **U+FE0E（VARIATION SELECTOR-15）不是** —— 它是**不可见的"文字呈现选择符"**，紧跟 `❤` 之后（`❤︎`，让爱心以文字灰色而非彩色 emoji 呈现）。这些游戏里它是**正常装饰**。

于是形成一条必然的失败链，正是用户看到的"部分长句译不出"：

```
原文含 ❤︎❤︎❤︎…（≥3 个 U+FE0E）
  → 模型忠实保留了这几个不可见字符（**正确的行为**）
  → 闸门数到 ≥3 个"乱码"，判 stray-chars 死刑
  → 重试时把"你的译文含乱码"喂回去，模型被误导
  → 最终退化：原样吐回原文 → unchanged → 再判死
```

**代价有多大**（`count-strays.js`，部署目录全部 `work\*-extract.json`）：

| 项 | 条数 |
|---|---|
| 语料（去重后原文） | 435,244 |
| 含 ≥3 个 U+FE0E（`❤︎`） | **7,644** |
| 含 ≥3 个 U+2015（`―`，日语破折号，同样被误列） | 750 |
| 合计被这条门槛否决 | **8,394（1.93%）** |

且高度集中：`SENNYU5`（3,695 条）、`牧场Ver1_1`（3,855 条）两个游戏就占了 7,550 条。**在这两个游戏里，含装饰符的长句会成片判死**，这就是"长句时常译不出"的真相 —— 不是模型翻不动，是闸门不让过。

**离线重判**（`rejudge.js`，拿已存下的运行记录按"去掉 U+FE0E"重算，不重新跑模型）：

| 运行 | 现在 | 放松字符类后 | 剩下的真缺陷 |
|---|---|---|---|
| 1.8B 改前 | 16/24 | **20/24 (83%)** | 2 条 `unchanged`、1 条 `\N<…>` 内被译（真错）、1 条 request-failed |
| 1.8B 关思考后 | 13/24 | **16/24 (67%)** | 同上量级 |
| 0.8B 关思考后 | 9/24 | 10/24 | **13 条 `unchanged`（把原文吐回来）+ 3 条 refused** |

## 七、结论：能否解决

1. **长句本身不是问题，不需要换模型、不需要改分句**。1.8B 在 400+ 字桶 3/3 通过。
2. **0.8B 的问题已解决一半**：`chat_template_kwargs` 修复让它从"完全不回话"变成"正常回话"（0→9/24）。剩下的一半**不是管线能修的** —— 它 13/24 条把原文原样返回，是模型能力问题；换针对 0.8B 调过的提示词也许能改善，但**不建议把 0.8B 当主力**，1.8B 明显更可靠且只慢 ~1.7 倍。
3. **用户感知的"长句译不出"可以彻底解决**，且是确定性的：把 U+FE0E（建议连带 U+FE0F）从 `quality.js:224` 的乱码字符类里拿掉，保留 `�` 与全宽泄漏串：

   ```diff
   -  const stray = d.match(/[―︎�]|ＥＮＤＩ|ＨＡＰＰＹ/g);
   +  const stray = d.match(/[―�]|ＥＮＤＩ|ＨＡＰＰＹ/g);
   ```

   预期 1.8B 从 16/24 → 20/24、并让 SENNYU5 / 牧场Ver1_1 里那 7,550 条装饰长句可以被正常翻译。`―`(U+2015) 建议**先保留**：它命中 750 条，需要单独取证确认它是不是也在抓某种真实乱码，再决定去留。

   **此改动尚未实施** —— 它会改变正在跑的翻译任务的判定行为（被判死的条目会转为重试），与"不影响翻译任务的状态"冲突，故留待确认。

生成时间：2026-10-12
分支：`v3-p1`
改动文件：`ui/MainForm.cs`、`ui/UiCheck.cs`
UiCheck：162 → **184 项**（新增 22 项）

## 一、改了什么

游戏列表第 4 列（原来标题「进度」）改为 **「翻译进度」**，内容从"百分比"改成一对计数：

```
975/9946        已译条数 / 需译条数
0/9946          一条都还没译，工作量照样看得到（百分比做不到这点）
```

原来的显示是 `45%` / `已译完`，**而且只在状态为「已汉化/部分汉化」时才显示**，其它游戏是空白。
现在只要这个游戏有可算的数据就显示计数。

## 二、两个数字从哪来

| | 来源 | 说明 |
|---|---|---|
| **已译条数** | `<stem>-translate-report.json` 的 `translated` | 管线自己的定义：本轮**命中缓存**的条目数（`entries.filter(e => cache.has(e.text)).length`），也就是"确实拿到译文"的条数 |
| **需译条数** | 后写入的那个文件：`-extract.json` 的条目数，或报告的 `entries` | 见下 |

**为什么需译条数要挑"最后写的那个"**：一次运行会在**开始**时重写抽取文件、在**结束时**写报告。
如果中途被打断（或只跑了 `extract` 模式），抽取文件是新的、报告还是上一轮的，
两者描述的条目集合**大小不同**。实测 `Detective Girl of the Steam City`：报告写的是 1052 条（上一轮残留的集合），
而盘上的抽取文件是 9946 条 —— 显示 1052 就把工作量说小了 9 倍。所以规则是：

```
抽取文件存在 且 抽取文件不早于报告  →  需译条数 = 抽取文件里的条目数
否则                              →  需译条数 = 报告里的 entries
```

抽取文件的条目数用 `CountExtractEntries()` 数：该文件是 `pipeline/index.js` 写出的紧凑 JSON 数组、
每条以 `{"id":` 开头，数这个标记即可（用窗口那个扁平读取器去解析 1.2 MB 文档只会更慢，也不会更准）。

## 三、一条界限：我们**跳过**的游戏不显示工作量

`已是中文` / `自带中文` 的游戏是被窗口跳过的（别人翻的，或本来就是中文），
对它显示"0/9098"就是在描述一件不存在的工作 —— 实测 `【御光盟国汉化组】露出女子校生2` 正是如此
（它状态是 `自带中文`，而盘上残留的抽取文件有 9098 条）。所以新增 `ShowsProgress(状态)`：
只有我们**会去翻**的状态才显示（`未汉化` / `未汉化（已还原）` / `未汉化（英文原版）` / `部分汉化` / `已汉化（本项目）`）。

悬停提示（tooltip）里除了 `已译 / 需译 条（百分比）`，在状态不是我们自己的工作时还会补一句
「已译条数取自上一轮完成的运行」—— 因为这一轮若被打断，报告里的数字就是上一轮的，状态列才是游戏本身的事实。

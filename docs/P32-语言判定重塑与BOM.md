## 一、现象与实测

`（游戏库）Detective Girl of the Steam City (eng-uncen) + save\…` 在界面里显示**已汉化**
（状态名 `自带中文`），因此被跳过、永远不会去翻。实测它到底翻没翻：

| 测量 | 数值 |
|---|---|
| live `www/data` 的 401 对白行 | **13,960 行，13,900 行英文、0 行中文** |
| `data_原版备份` 的同批对白 | 完全相同（13,900 行英文） |
| 该游戏的翻译缓存 | 4,724 条，**全部"日文→中文"**（键如 `打撃/物理`），**没有一条英文** |

结论：**这局确实没翻**（玩家看到英文），历史上的补丁只写过 1,737 处名词/词条，对白一条没动。

## 二、为什么会被判成「自带中文」

`tools/game-state.js` 的判据是"**假名占 CJK 字符的比例**"（`byteProfile` 只数假名和汉字，**完全不计拉丁字母**）：

```
backup 假名 6,605 / 汉字 13,531  →  32.8%
CN_MAX = 35   →  32.8 < 35  →  "原版数据即中文"  →  自带中文
```

对中文/日文游戏这个比例有意义（非 ASCII 文本几乎全是 CJK）；对**英文游戏**它是"少数内部的比例"，
13,531 个汉字里混进几千个假名就能把它推到 30% 上下——**这个数字不代表语言**。判据从来没问过
"这游戏是不是拉丁文字"。

> 你猜的 "mtool 被检测"：MTool 的文件（`TrsData.bin` 2.2 MB、`data_汉化备份`、`一键恢复汉化.bat` /
> `一键还原汉化前.bat`）确实都在，但在旧代码里它们只影响备注文字和 `installedByUs` 标记，
> **不是** `自带中文` 的来源。

## 三、最终判定方式：**按"玩家读到的文本"判语言，不按字节**

关键在"用什么衡量"。最终实现是：

1. **`textProfile(dataDir)`（新）**：把数据目录**按抽取器的判据**过一遍（`mv.extract` 选出的、真正会被送去翻译的字符串），
   在**这些文本里**数假名/汉字/拉丁字母。英文对白 → 拉丁 ≥ 97%；中文对白 → 拉丁接近 0。
2. **`isLatinText(p)`**：`latinPct ≥ 70%` 且字母总量 ≥ `CJK_MIN`（200）。只看"可译文本"的画像。
3. **新状态 `未汉化（英文原版）`**，在 JSON 路径（MV/MZ）里判定一次：
   位置在**中文 locale 检查之后**（`resources/zh-CN` 是中文发行版的直接证据），**所有依赖 CJK 比例的分支之前**。
   状态名以「未汉化」开头，界面的 `Skip = 已是中文/自带中文` 天然不再跳过它。
4. **`byteProfile` 的两个比例都加了 `CJK_MIN ≥ 200`** 门槛：22 个字符算出的比例是噪声，不足为凭。
5. `无文本` 的判据改为"既没有可译文本、也不是拉丁语文本"，否则一个有上万行英文对白的游戏会被说成"文本太少"。
6. 导出内部函数（`classify/textProfile/byteProfile/isLatinText/verdictFromBytes/locate/findBackup/常量`），
   CLI 收进 `require.main === module` —— `require` 它不再会去扫 `（游戏库）`。

### 现在这局的判定

```
未汉化（英文原版）  原版是英文（可译文本的字母里拉丁占 98.6%，340671 个字母，共 9891 条文本；
                    假名占比 0.3% 只是 CJK 内部比例），本工具曾处理过
```

## 四、第一版是错的，以及它为什么错（重要）

第一版把拉丁比例算在**目录字节**上，并在**两条路径**都加了判据。跑一遍全库旧状态文件里
被判为「自带中文/已是中文」的 14 个游戏做核对——**14 个全部翻盘**：

```
  改变  自带中文 → 未汉化（英文原版）   【御光盟国汉化组】露出女子校生2      原版是英文（拉丁字母 91.1%）
```

**露出女子校生2 是真正的汉化组中文版**（对白全中文、自带 `resources/zh-CN`），把她说成"英文原版"就是新的错误。
原因：**字节里大部分不是玩家读到的文本**——

- RPG Maker 的 JSON 到处是键与结构（`events`/`pages`/`list`/`parameters`），这些也是拉丁字母；
- VX Ace 的 `.rvdata2` 里**嵌着整份 Ruby 脚本**，所以一个中文游戏也能量出 89% 拉丁
  （实测 `莉娜的金钱探索`：归档 89.2% 拉丁，而它玩起来是中文）。

也就是说，我第一版犯了和旧判据同型的错误：**拿一个与"语言"无关的量去判语言**。

修正后的复核结果（同一批 14 个游戏）：

| 结果 | 游戏 | 依据 |
|---|---|---|
| **改变 → 未汉化（英文原版）** | Detective Girl of the Steam City (eng-uncen) | 可译文本 98.6% 拉丁 |
| **改变 → 未汉化（英文原版）** | Beautiful Girl Detective El | 97.2% 拉丁 |
| **改变 → 未汉化（英文原版）** | Midnight Exhibition JK 2 ver.1.00 **[EnglishMTL]** | 99.8% 拉丁 |
| 不变（自带中文） | 【御光盟国汉化组】露出女子校生2 | 假名 5.0%，字节路径 |
| 不变（已是中文） | 莉娜的金钱探索 | 归档，假名 22.1% |
| 不变 | 无知少女的乡村韵事 / Yutaka Gaiden / [官中]女盗贼希露菲 / Ｈ？英知？爆乳研究員 / youshicun / 莎娜 / Country Girl Keiko | 假名 1.9%–15.4% |

**3 个改变，且都是真英文版**。

### 已知限制（写进单测，不假装已解决）

**VX/VX Ace 与归档仍然只按字节判**，没有拉丁判据：判断它们的语言需要按游戏跑一遍 Ruby 抽取器，
而字节里的拉丁含嵌进脚本的 Ruby，不能作依据。所以 `Country Girl Keiko`、`莎娜` 这类 VX 游戏的判定没有变——
它们是不是英文版，这一版**没有解决**，单测里有一条断言把这个缺口钉住。

## 五、顺带修掉：`System.json` 因为 BOM 被整个跳过

同一局的补丁报告里有一条一直没人发现的错误：

```json
{"file":"System.json","err":"parse: Unexpected token '\uFEFF', \"{\"airship\"... is not valid JSON"}
```

RPG Maker MV 给部分数据文件写了 **UTF-8 BOM**，`JSON.parse` 拒绝它。`pipeline/` 里**没有任何一处**剥 BOM
（查过全部 5 个从游戏目录读 JSON 的位置），全部是 `catch (e) { continue; }` —— `System.json`（`terms` 整块：
菜单词、保存/读档提示、技能类型与属性名）**既没被抽取也没被回填**，报告只说"244 条 missing"。

改法：`pipeline/extract/mv.js` 新增并导出 `readJsonFile(full)`（剥 `\uFEFF` 再 parse），
`pipeline/patch/mv.js` 与 `pipeline/extract/resources.js` 一律走它；**回写时若原文件有 BOM 就补回去**。

## 六、验证

- `tools/unit-game-state.js`（**31 项**）：英文原版 → `未汉化（英文原版）`；英文原版+英文备份 → 仍不是自带中文；
  中文原版 → 仍是 `自带中文`；中文数据无备份 → `已是中文`；日文原版 → `未汉化`；
  **回归**：一个"字节里 99% 拉丁、但可译文本是中文"的合成游戏——按字节像英文、按文本是中文，
  判定必须保持 `已是中文`（这正是第一版翻车的形状）；`textProfile` 只统计可译文本；
  以及"byte 路径仍判 自带中文"的已知限制断言和 `LATIN_TEXT_PCT`/`CJK_MIN` 边界。
- `tools/unit-event-codes.js`（**21 项**）：新增"带 BOM 的 System.json"——词条照常抽出、替换、无解析错误、
  回写后 BOM 仍在。
- 其余 15 套全绿。
- 部署目录已同步（`pipeline/` 3 个文件、`tools/*.js` 25 个文件）。**状态由 `tools/` 决定，不需要换 exe**。

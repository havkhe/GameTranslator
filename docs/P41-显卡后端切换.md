## 一、为什么要切换：CUDA 12 的包不支持 GTX 10 系

CUDA 12 的预编译包**只带 sm_70 及以上的内核**（Volta / Turing 起，即 RTX 20 系往上）。
GTX 10 系是 Pascal（sm_61），装上 CUDA 版后 llama.cpp 会**静默退回 CPU**——能跑，但慢得多。
所以这台机器（**6GB 的 GTX 10 系（Pascal）**）正确选择是 **Vulkan**，而 RTX 机器用 CUDA 12 更快。
以前只能手工执行 `download-llama.ps1` 把整个 `llama` 目录换掉，两套不能共存。

## 二、两套并存 + 一键切换

**布局**（包里就是两种都有）：

```
llama\
  vulkan\llama-server.exe    ← 默认：老 NVIDIA / AMD / Intel 都能用
  cuda12\llama-server.exe    ← 需要 sm_70+，自带 cudart64*.dll
  BACKENDS.txt               ← 两套各是什么、怎么切、怎么更新
```

切换是**一个设置 + 一次重启**，不下载、离线可用：

1. **窗口里**：模型行最右边新增按钮 **「后端：Vulkan / 后端：CUDA 12」**（点击即切换）。
   - 有服务在跑且**没有翻译任务**时，自动「停止 → 启动」，切换立刻生效；
   - **翻译进行中会拒绝**（服务器正在为当前这一局服务，停掉它会让整批失败）；
   - 所选后端的文件夹不存在时，**提供一键下载**（在窗口进程内直接下载 + 解压，见下）；
   - 切到 CUDA 12 前会检查显卡：没有 sm_70+ 的 NVIDIA 卡会**先警告**再切；
   - 状态行（任务进度栏「模型：… 端口：… 」那一行）末尾会写 **后端：vulkan / cuda12**，
     如果所选后端与实际安装的不是一个，会跟一句「（实际：…）」；文件夹缺失则写「（未安装：…）」。
2. **根目录里**：双击 **`切换显卡后端.bat`**（菜单式），或执行
   `.\switch-backend.ps1 -Backend cuda12`（不带参数则只显示当前状态与安装情况）。
   两者都只改 `ui-settings.ini` 里的 `LlamaBackend=` 一行，**其它设置原样不动**。

**向后兼容**：老的单目录布局（`llama\llama-server.exe`）**照旧可用** —— 找不到 `llama\<backend>\` 时
自动回落到 `llama\` 本身，所以现有安装什么都不用改。ini 里没有 `LlamaBackend` 时按 `vulkan` 处理。

## 三、顺带修掉的下载器 bug（两个都是真 bug）

1. **`download-llama.ps1` 下载不到东西**：它调 `/releases/latest`，而现在 llama.cpp 的 latest 是
   **semver 版本（v0.6.0）**，里面只有一个 `nightly-tag.txt`、**没有任何 zip** → 直接 `WebException`。
   这与用户实测一致（"CUDA 版下载失败"）。
   改法：拉 `releases?per_page=30`，取**第一个真正带 Windows 二进制包的 bXXXX 版本**
   （实测现在可用的是 `b11571`）；`-Tag` 仍可手动钉住。
2. **CUDA 版缺运行库**：CUDA 构建**还需要同目录的 CUDA 运行库**（`cudart64*.dll`），
   llama.cpp 把它单独发成 `cudart-llama-bin-win-cuda-12.4-x64.zip`。老脚本只下主包 →
   即使在 RTX 机器上，装出来的 CUDA 版也**起不来**。现在两个包都下，并在缺少 `cudart64*.dll` 时明确报错。

窗口内的"一键下载"是**进程内**实现的（`WebClient` + `ZipFile`），**不起 shell**：
拿设置里的路径去拼命令行属于把用户输入交给 shell，而且还要看那台机器的 PowerShell 执行策略。
每次请求都过 `GuardGithub()`：**只允许 https**，主机**白名单**（`github.com` / `api.github.com` /
`objects.githubusercontent.com`），字面 IP 里的回环/内网/保留地址一律拒绝。
（为此给两个构建脚本加了 `System.IO.Compression.FileSystem.dll` 与 `System.Management.dll` 两个引用。）

### CUDA 二进制怎么进的包（最终做法，2026-10-13）

结论：**两套后端都打进主包**（`llama\vulkan\` + `llama\cuda12\`），CUDA 侧取自 llama.cpp 官方
预编译包，逐字节校验后才采用。步骤与依据：

1. **取件**：`cuda-fetch.ps1`（本目录）经代理下载上游 `b11571` 的两个 zip——
   `llama-b11571-bin-win-cuda-12.4-x64.zip`（265,226,405 B）与
   `cudart-llama-bin-win-cuda-12.4-x64.zip`（391,443,627 B，含 CUDA 运行库与 cuBLAS）。
   脚本内**写死了这两个文件的 sha256**（取自 GitHub API 的 `digest` 字段，2026-10-12 实测逐字节相符），
   所以它要么产出与上游完全一致的文件，要么直接报错——不会悄悄塞进半个包。
2. **解压**：把两个 zip 解到同一个目录 `llama-cuda12\`（55 个文件 / 1,140.9 MB，
   含 `llama-server.exe`、`cudart64*.dll`、`ggml-cuda*.dll`、`cublas64_12.dll`）。
3. **装包**：`make-package-31.js` 把部署里的 Vulkan 构建放到 `llama\vulkan\`、把 `llama-cuda12\`
   放到 `llama\cuda12\`，并写 `BACKENDS.txt` 说明两套是什么、怎么切。
   该脚本**要求 CUDA 目录必须存在**（缺失即抛错），避免误出一个只有 Vulkan 的包。
4. **打包器为什么是 Compress-Archive 而不是更快的 `tar.exe`**：实测 `tar.exe -a -c -f x.zip`
   产出的条目**不带 UTF-8 语言标志（bit 11）**，包内的 4 个中文名（`使用说明.txt`、`安装说明.txt`、
   `应用新版本.bat`、`切换显卡后端.bat`）在中文 Windows 上会显示成乱码；
   `Compress-Archive` 会正确置位（实测 bit11 已设、名字 UTF-8 往返一致）。
   本机没有 7-Zip 或 Info-ZIP `zip` 可用，所以宁可慢也用对的。
5. **未装机**：CUDA 仍然**不部署到本机** `D:\GameTranslatorV3`，那里只有 Vulkan；这只影响出货包。

**代价（如实写）**：主包从约 133 MB 增到约 770 MB。老卡用户其实只用得到 Vulkan 那 90 MB，
所以发行说明里写明"想小包就删掉 `llama\cuda12\`，程序能再下回来"。

**暂存区只留脚本、不留大文件**：出货后两个上游 zip（626 MB）与解压目录（1,141 MB）已删除，
共腾出 1.77 GB；`cuda-fetch.ps1` 随时能经代理在约 4 分钟内重新下载、校验并解压出它们。
包里那份 `llama\cuda12\` 当然不受影响（它是装包时复制进 `GameTranslatorV3-v3.1\` 的）。

### 代理：本机取 GitHub 文件的正确姿势（用户开启代理后实测）

本机直连 GitHub 是 ~30 KB/s；用户在 `127.0.0.1:7897` 开了代理（Clash，`ProxyEnable=1`）后，
**走代理 453 KB/s —— 快 15 倍**（626 MB 从 6 小时降到约 25 分钟）。三个要点：

- **curl 不会自动读 Windows 的系统代理**（它只看 `http_proxy`/`https_proxy` 环境变量，这台机器
  两个都没设），所以命令行取文件必须显式加 `-x http://127.0.0.1:7897`；
- **产品自身的两条下载路径不用管**：`DownloadBackendAsync` 用 `WebClient`、
  `download-llama.ps1` 用 `Invoke-WebRequest`，两者**默认就读系统（WinINET）代理**，
  所以用户开了代理之后，程序里的「后端：…」一键下载会自己走代理 ✓（无需改代码）；
- 代理刚开启的一两分钟里，GitHub 资产的重定向主机 `release-assets.githubusercontent.com`
  可能先回 `502`/连接被重置，**重试即可**（实测第二次就通）。

另外，PowerShell 5.1 的 `Invoke-WebRequest` 单独取这种 250 MB+ 的文件会**卡在 0 字节**
（`-OutFile` 20 分钟不动），本机取大文件统一用 `curl.exe`。

## 六、GTX 10 系（Pascal）实测：CUDA 能用，但不一定更快（2026-10-13）

用户问「1060 6G 能否用老版本 CUDA 加速」。结论有两半，前半推翻了我们之前写下的说法。

### 6.1 之前那句"不支持 Pascal"是错的

发行说明、两本手册、`BACKENDS.txt`、`download-llama.ps1`、`switch-backend.ps1` 以及程序里
`CudaLooksUsable()` 的警告，都写着"CUDA 12 预编译包不支持 GTX 10 系 / 会静默退回 CPU"。
实测证据（三条，互相印证）：

- 扫包里的 `ggml-cuda.dll`（545.8 MB）里的 fatbin 架构标记：**`sm_50 / sm_61 / sm_70 / sm_75 /
  sm_80 / sm_90` 各 144 处** —— **sm_61（Pascal）在内**；
- `llama-cli.exe --list-devices`（就在包里那套 CUDA 二进制）：`CUDA0: NVIDIA GeForce 6GB 的 GTX 10 系（Pascal）`，
  加载日志写明 `compute capability 6.1`；
- `llama-bench` 在 CUDA 上真跑出 601 t/s 的预填充（退回 CPU 只会有个位数），**没有**静默退回。

已更正的地方：`安装说明.txt`、`使用说明.txt`、`docs/release-note-v3.1.txt`、`BACKENDS.txt`（由
`make-package-31.js` 生成）、`download-llama.ps1`、`switch-backend.ps1`，以及程序里的警告文案。

### 6.2 代码：警告从"不支持"改成"不一定更快"

`CudaLooksUsable()` 这个名字本身就是旧假设。改成两个**纯函数**，便于 UiCheck 在任意机器上断言：

```csharp
internal static bool NameLooksLikeNvidia(string name)          // 是不是 N 卡（任何 N 卡都能跑 CUDA 构建）
internal static bool NameLooksLikeModernNvidia(string name)    // 是不是"CUDA 通常更快"那一档（Turing sm_75+：
                                                               // RTX 20/30/40/50、GTX 16 系、T4/V100、A/L/H 系）
private bool CudaIsUsuallyFasterOnThisGpu()                    // 上面那个的 WMI 版本，只决定"要不要提醒"
```

`GTX 10 系（Pascal）` 现在被正确分类为"能跑 CUDA，但不在通常更快的档里"，切换时只**提醒**、不再拒绝。
UiCheck 253 → **282** 项（新增 11 条：GTX 10 系（Pascal）/970/1650/1660S、RTX 3060/4090、Intel 核显、A 卡、空名）。

### 6.3 实测数据（6GB 的 GTX 10 系（Pascal），驱动 582.66，`-ngl 99`）

| 模型 | 后端 | 读入 pp256 | 生成 tg |
|---|---|---|---|
| Hy-MT2 **1.8B Q8_0** | CUDA | **1451 t/s** | **46.3 t/s** |
| | Vulkan | 367 t/s | 28.3 t/s |
| Galtransl-v4 **4B Q6_K** | CUDA | **601 t/s** | 25.5 t/s |
| | Vulkan | 257 t/s | **38.2 t/s** |
| Qwen3.5 **4B Q4_K_M** | CUDA | **595 t/s** | 27.1 t/s |
| | Vulkan | 276 t/s | **37.3 t/s** |

（`-n 256` 复测生成速度，结论不变：CUDA 25.5 / Vulkan 38.2。）显存不是瓶颈：6 GB 里空着 5.5 GB。

**规律**：CUDA 在**读入（预填充）**上快 2~4 倍；**生成（出译文）**这一步，
**Q8_0 类量化 CUDA 明显更快**，而 **4B 的 K 量化（Q4_K/Q6_K）反而 Vulkan 更快**。
原因在 Pascal 本身：没有 tensor core、FP16 只有 1/64 速率，K 量化在 CUDA 上要走反量化；
Vulkan 那边用的是整数点积（`int dot: 1`）。
翻译的批是"长输入 + 差不多长的输出"，所以 4B K 量化下 **Vulkan 端到端反而快约 20~50%**。

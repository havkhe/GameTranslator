# P9 —— 启动慢的根因与"游戏状态"同步

对象：`D:\GameTranslatorV3`（部署目录）与仓库 `ui/`、`tools/`。承接 `docs/P8-后续修复报告.md`。

---

## 一、启动为什么慢：ListView 每行约 310 毫秒

### 现象

窗口在 1.5 秒内出现，然后就**卡住约 34 秒**才可用。启动追踪日志（`work\startup-trace.log`）显示，
主线程在窗口构造完成后再过 34 秒才进入消息循环：

```
+  1045ms  MainForm constructed (handle=… visible=False)
+ 35452ms  OnLoad 触发, visible=True          ← 34.4 秒之后 Load 才触发
```

### 定位过程（每一步都是实测，不是推断）

1. **不是启动扫描**：启动时不扫描游戏库，`ScanAllRoots` 只在点击按钮时调用。
2. **不是构造耗时**：`MainForm` 构造总计约 1.0 秒（界面 375ms、模型列表 314ms、游戏列表 328ms，110 个游戏）。
3. **不是消息循环本身**：把窗口显示拆出来后计时，裸循环 0.5 秒就正常 tick。
4. **逐控件建句柄计时**（临时诊断，已移除）直接点名了：

```
慢控件 34375ms  SplitContainer/SplitterPanel/Panel/ListView
逐控件建句柄：共 49 个，用时 34402ms
```

5. **是行数，不是控件**：只加载 10 个游戏 → 3.1 秒；110 个 → 34.4 秒。**线性，约 310 毫秒/行。**
6. **成本发生在行进入原生控件的那一刻**：ListVievw 句柄不存在时填 110 行只要 326 毫秒；
   句柄一旦存在（即窗口已显示），同样的填充变成 35 秒。这也解释了为什么"先显示窗口再填列表"
   只是把卡顿从"窗口不出现"变成"窗口出现但僵住 35 秒"。

### 修复：虚拟模式

`ui/MainForm.cs` 的游戏列表改为 `VirtualMode = true`，行按需生成（`RetrieveVirtualItem`），
不再向原生控件推送任何一行：

* `RefreshList()` 只发布行数（`VirtualListSize`），不做任何可能阻塞的工作
* 勾选状态以模型（`_games`）为准，事件用 `ItemCheck`（虚拟模式下才有 `e.Index`/`e.NewValue`）
* 选中项从 `SelectedIndices[0]` 映射回模型（虚拟模式没有 `SelectedItems`）
* 全选/取消全选先改模型，再 `RedrawItems` 刷新可见行

**实测结果（同一台机器、同一份 110 个游戏的列表）**：

```
修复前：+1039ms Application.Run 之前 → +35452ms 窗口显示      （34.4 秒）
修复后：+1052ms Application.Run 之前 → +1121ms 窗口已显示     （0.07 秒）
```

**顺带修掉了"窗口创建但不显示"** —— 那个症状一直存在，只是被启动器里的原生 `ShowWindow`
掩盖着。它其实是同一个 34 秒阻塞的副产品：主线程卡在 `Visible = true` 里，Load 永不触发、
定时器永不运行。阻塞消失后，正常的显示路径自己就好了，因此：

* 启动器不再在消息循环之前操作窗口（`Program.cs` 删掉了预显示与后台重试线程）
* `MainForm` 里"用后台线程 `BeginInvoke` 去强制显示"的那段也删掉了，改成一个本线程的
  WinForms 定时器兜底（它只在窗口真的没显示时才动手）
* `OnShown` 只保留一句追踪，用来在日志里记下"窗口何时真正出现"

### 保留下来的东西

* `work\startup-trace.log` 现在带**毫秒计时**（`+1027ms` 这种），一次启动一行线索；
  这次能定位到行级成本，全靠它
* `GT_INSTANCE_NAME` 环境变量可改互斥体名，便于在用户的窗口开着时另起一个实例做验证
* `build-ui.bat` 增加 `ui\Startup.cs`

### 附带发现（尚未处理）

`UpdateModelState()` 在构造与每次 `UpdateButtons()` 里各做一次"连一下 127.0.0.1 端口"，
用 `TcpClient.BeginConnect` + `WaitOne(300)` + 提前 `Dispose`。它没有造成这次的 34 秒，
但启动路径上不需要它 —— 状态标签由 1 秒的定时器刷新就够了。留待后续。

## 二、游戏库状态：本来就中文 / 已汉化的，同步到 UI

### 判据（`tools/game-state.js`）

判据不看任何历史记录，只看游戏本身：

| 证据 | 说明 |
|---|---|
| 玩家可见对话（`resources/<locale>/`） | 仍带假名的比例，原版备份提供分母 |
| 数据逐字段对比原版 | 只统计**管线会翻的字段**（事件文本参数 + `rules.TEXT_FIELDS`）：原版带假名、现在不带 → 已译；两边都带假名 → 仍未译 |
| `data_原版备份` 存在且是日文 | 说明这里被本项目翻过（或翻过又被还原） |
| `一键恢复汉化.bat` / `一键还原汉化前.bat` | 本项目安装过的痕迹 |
| `resources/zh-CN` 等非 ja 语言目录 | 自带中文语言包（官方中文常见形态：ja-JP 仍是日文） |

**踩过的坑**：一开始用"数据目录里假名占比"当判据，结果把已翻好的游戏算成"部分汉化"——
因为管线刻意不翻脚本/插件块里的日文。实测 `凍堂ヒロカの隷雄譚` 按那个口径只有 24% 中文，
按对话口径是 **97%**；`メアリ` 按前者算 50%，按"管线会翻的字段"算是 **95%**。
现在的判据对这批游戏全部给出合理数字。

### 状态取值

```
已汉化（本项目）    覆盖 ≥90%，且有原版备份/安装痕迹
部分汉化            覆盖 30–90%
未汉化（已还原）    有原版备份但当前数据是日文（备份与缓存还在，重译很快）
未汉化              没有备份，数据基本是日文
自带中文            自带非日文语言目录且是中文
已是中文            数据已是中文但没有本项目的痕迹
VX Ace / VX / 打包归档 / 非 MV/MZ    本工具不覆盖
```

### 结果（UI 当前列出的 110 个游戏）

```
54  未汉化（已还原）        有原版备份、当前数据是日文（备份与缓存还在，重译很快）
17  未汉化                 无备份，数据基本是日文
15  VX Ace                 .rvdata2，本工具不覆盖
14  打包归档                Game.rgss3a 等，需先解包
 6  部分汉化
 4  已汉化（本项目）
```

抽查（与 P8 的独立复核一致）：

| 游戏 | 状态 |
|---|---|
| `凍堂ヒロカの隷雄譚` | 已汉化（本项目）对话 97% |
| `メアリの悪徳政治家お屋敷潜入捜査` | 已汉化（本项目）已译 95% |
| `陰キャなベルちゃんは隠れド変態マゾ便器！` | 已汉化（本项目）已译 94% |
| `RJ300498-v1.2` | 部分汉化 68% |
| `私が変態サキュバスに堕ちるまで` | 部分汉化 90% |
| `BITCH FAMILY ON THE BEACH` | 部分汉化 64% |
| `本編`（RJ01081992） | 部分汉化 35% |
| `youshicun` | 部分汉化 4%（**目录名标着官方中文，但数据仍是日文** —— 目录名是主张，数据是证据，两者不一致时如实标出而不替用户下结论） |

**两组数字都出现过，别被绕晕**：修好判据之前，"部分汉化"一度有 27 个——那是分母把脚本/插件块
也算进去后的虚高（只译了几百串的游戏能算到 50%）。换成"只统计管线会翻的字段"后，落点是
上面这一组；`youshicun` 从 50% 掉到 4% 就是这个修正的直接结果。

### UI 变化

* 左侧工具栏新增 **「刷新状态」**：调用部署目录里的 `node\tools\game-state.js`，
  结果写入 `work\games-state.json`，然后重载列表。子进程执行，不占用界面线程。
* **状态列**显示上表取值；未读过状态文件时回落到旧的"已是中文，默认跳过"标记。
* `work\games-state.json` 里除了状态还带**证据**（各文件的行数、假名比、对话数、语言目录画像），
  便于核对判据而不是只信结论。
* 状态由工具计算，不由 UI 猜测；UI 只负责显示。

### 部署要求

`tools\` 目录现在必须在部署目录里（`（部署目录）tools\`），
因为「刷新状态」按钮运行的是部署副本。已部署 9 个脚本。

# P18 —— 任务进度：每秒 token 数、每分钟条数、完成时间预测

对象：`ui/MainForm.cs`、`ui/UiCheck.cs`。承接 `docs/P17-暂停粒度.md`。管线本轮未改动。

## 一、面板上新增什么

「任务进度」里原来的单行「速度」拆成两行（面板高度 190 → 210，网格 8 行 → 9 行）：

```
速度：28.4 tok/s（近 15 秒）    41.2 条/分    已知已译 1958 条
预计：本局 5 小时 52 分    |    本批 8 小时 10 分（剩余 3 局、12,345 条），另有 2 局大小未知
```

- **tok/s**：来自服务器自己的计数器；
- **条/分**：来自管线 `PROGRESS` 行里的已译条数（跨游戏累计）；
- **本局预计**：本局剩余条数 ÷ 速率；
- **本批预计**：本局剩余 + 其余未完成游戏各自进度报告里的剩余条数，除以同一个速率。

暂停时这两行改显示 `速度：已暂停（当前请求结束后不再发出新请求）` / `预计：已暂停`。

## 二、数字从哪来

| 数字 | 来源 | 说明 |
| --- | --- | --- |
| 累计生成 token | `GET /metrics` → `llamacpp:tokens_predicted_total` | 复用已有的后台探测（每 ≥3 秒一次，只读短请求） |
| 已译条数 | 管线的 `PROGRESS <cached> / <total>` 行 + 本运行已结束各局的累计 | 跨游戏连续 |
| 本局总数 | 同一条 `PROGRESS` 的 `<total>` | |
| 其他局剩余 | 各局 `-translate-report.json` 的 `entries` − `translated` | 走已有的 `TryReadProgress`（每局只读一次并缓存） |

## 三、四个刻意的设计点

1. **每 15 秒采样一次，而不是实时读**（`RateWindowSeconds = 15`）。两个计数器都是**突发式**增长的（每隔几秒才有一条回复），瞬时读数会剧烈跳变，建立在其上的"预计完成时间"也会跟着跳。
2. **计数器回落保护**：一台机器上可能有两个服务同时监听一个端口（llama.cpp 设了 `SO_REUSEADDR`，Windows 允许——本会话实测过），它们**各自维护自己的计数器**。所以 `/metrics` 的读数可能来自不同进程、数值反而变小。此时**重置基线**而不是报出负速率。
3. **解析 `/metrics` 必须跳过注释行**：`# HELP llamacpp:tokens_predicted_total Number of tokens …` 里带着同名指标，而它的"值"列是一个单词。朴素的子串查找会捞到这一行、拿到非数字。`ParsePredictedTokens` 只认非 `#` 开头、且值必须是数字的行。（我在自己的临时脚本里恰好踩过这个坑，所以它现在是断言之一。）
4. **"大小未知"如实标注，不当成 0**：从未翻译过的游戏没有进度报告，无从得知它有多少条。把它算作 0 会让预计严重偏乐观 —— 界面直接写「另有 N 局大小未知」。速率为 0 时也必须说清楚，而不是显示一个假的"0 秒"：
   `预计：—（等 15 秒统计出速率）`，并在 tooltip 里解释"计数器刚重置、或这段窗口刚好没有新译文"。

## 一、搜索栏为什么会"找不到"

P35 里的搜索行是加在**工具栏下面、列表上面**的。两个原因让它不好找：

1. **在最不容易被看到的那一行**：左边那一列从上到下是 任务队列 → 工具栏 → 列表，搜索行夹在工具栏和列表之间，
   只有 30 px 高、没有边框；
2. **更主要的**：你可能还没换 exe —— P35 的搜索框是随那次构建一起暂存成 `GameTranslatorV3.exe.new` 的，
   **不双击 `应用新版本.bat` 就不会生效**（这是这套部署一直的规矩：exe 不能覆盖正在运行的程序）。

现在改成**左侧面板的第一行**（任务队列和工具栏之上），加了边框、加高到 34 px：

```
┌─ 搜索游戏名：[____________________]      显示 12 / 139  [清除] ─┐
│ 任务队列（按组顺序执行）                                          │
│ 工具栏：扫描文件夹 添加游戏 扫描全部路径 重新扫描全部 …            │
│ 游戏列表                                                          │
```

Docking 的规则是"从控件集合的末尾往前解析"，所以搜索行要在 `BuildQueuePane()` **之后**加入才会落在最上面 —— 代码里注明了这一点。

## 二、点列标题排序（游戏 / 引擎 / 翻译进度 / 状态）

点一次升序、再点一次降序，列标题上带 **▲ / ▼**（箭头只留在当前排序列），底部计数行同时写「排序：游戏 ▲」。
「选」这一列不参与排序。

| 列 | 排序依据 |
|---|---|
| 游戏 | 名字，`CurrentCultureIgnoreCase`（中文/日文名按当前区域顺序，不是码位顺序） |
| 引擎 | MV / MZ / VX / VX Ace 分组 |
| 翻译进度 | **完工比例** done/entries；没有数字的游戏排最后 —— 「未知」不是 0%，排在最前会把已完成的游戏埋掉。比例相同时大工程在前（`0/9946` 与 `0/190` 不是一回事） |
| 状态 | 状态名（未汉化 / 已汉化 / 已是中文…），同类相邻 |

**排的是模型（`_games`），不是显示副本。** 理由：列表顺序同时就是批次里游戏的执行顺序，
如果"看到的顺序"和"跑的顺序"不一致，那是个陷阱。排序只重排同一批 `GameItem` 对象，
所以勾选状态、已缓存的进度、队列（存的是路径不是对象）都跟着各自的游戏走。排序后立刻写一次
`games-cache.json`，保存的顺序与显示的顺序一致。

翻译进行中排序是**安全**的：批次在开始时就对已勾选的游戏取了快照（`StartTranslation`），
重排列表改变不了正在翻译的内容。

翻译进度这一列排序前会先把每个游戏的数字读一遍（读 work 目录），读完缓存在条目上，
再点第二次就不再读文件了。

## 三、验证

UiCheck 234 → **242 项**，全部通过（部署目录、用部署自身源码构建）：

- 按「游戏」升序：139 行的名字确实有序；列头带 ▲；
- 再点同一列：降序，列头带 ▼；
- 按「状态」排序：同类相邻；**箭头只留在当前排序列**（`选 | 游戏 | 引擎 | 翻译进度 | 状态 ▲`）；
- 检查结束后把顺序**原样写回**（含 `games-cache.json`），跑检查不留痕。

> 写这段测试踩到一个 C# 细节：`GameItem` 是**私有的嵌套类**，`((dynamic)o).Name` 会在运行期抛
> `RuntimeBinderException: "object"未包含"Name"的定义` —— 动态绑定看不见私有类型的成员。
> 改用 `o.GetType().GetField("Name").GetValue(o)` 反射读取。

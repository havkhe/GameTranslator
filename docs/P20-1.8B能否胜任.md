生成时间：2026-10-11
分支：`v3-p1`
测量脚本：`D:\dsh\gt-audit\p20\workload.js`（剩余工作量）、`bench-mixed.js`（真实混合吞吐）、`dump-pairs.js` / `kana-residue.js` / `summary.js`（质量）、`probe.js` / `wait.js`
测试环境：`llama-server` 起在**独立端口 18099**（避开程序自己的 18080，全程不碰正在运行的翻译任务），测完已退出、显存归还

## 一、结论

| 问题 | 答案 |
|---|---|
| 速度扛得住吗？ | **扛得住。** 实测 **146 条/分、50 字/秒、53 tok/s**；剩余 32 万条 ≈ **37 小时**、620 万字 ≈ **34 小时** → 约 **1.5 天连续跑完**。换 4B 约 2.2 天 |
| 短条目翻得好吗？ | **好。** 真实混合样本 80 条（均值 20 字）通过 **76/80 = 95%**，管线自动批量（10 个请求送 80 条，约 8 条/请求） |
| 长句翻得好吗？ | 16/24（67%），失败主要是闸门误判 U+FE0E；放松后 20/24，400+ 字桶 3/3。**长句不是 1.8B 的短板**（见 `docs/P19`） |
| 那短板是什么？ | **日文残留。** 1.8B 输出里 **13.16%** 的条目仍带假名（人名 `フラン`，甚至整词整句 `オナホとして`／`ちょっとおまんこが`／`びくんびくん`）；而部署里现有 15.5 万条已译缓存只有 **0.47%**。**差 28 倍** |
| 一句话 | **能跑完，但成品约每 7~8 条里有 1 条带日文残留**。要干净成品就上 4B（只慢 1.4 倍，残留降到 0.5% 量级） |

## 二、工作量实测（`workload.js`）

只读管线自己的产物：`work\<game>-extract.json` + `work\<game>-translations.json`。

```
已抽取游戏        74 个
条目总数          435,244（去重后相同）
已有可用译文      112,092（25.8%）
待译              323,152（74.2%）
待译原文总字符    6,186,764
```

待译条目的长度分布 —— **这是 1.8B 能撑住的根本原因**：

| 长度 | 条数 | 占比 |
|---|---|---|
| < 20 字 | 173,359 | 53.6% |
| 20-49 字 | 145,650 | 45.1% |
| 50-99 字 | 4,005 | 1.2% |
| ≥ 100 字 | 138 | 0.03% |

**98.7% 是 50 字以下**（道具名、技能名、系统文本、短对白），不是剧情长文。所谓"长句问题"覆盖的只是那 1.2%。

剩余量最大的几局：`_OreNo小屋…魔法少女`（26,163 条 / 53 万字）、`灼炎 巫女 静音…浄化物語`（19,675 条 / 43.7 万字）、`Game`（22,605 条 / 43.4 万字）、`youshicun`（24,166 条 / 42.9 万字）、`牧场Ver1_1`（18,510 条 / 41.5 万字）、`SENNYU5`（16,762 条 / 37.7 万字）。

## 三、吞吐实测（`bench-mixed.js`）

从最大的真实抽取文件（`_OreNo小屋…`，26,163 条）按**系统抽样**取 80 条，长度分布与全语料一致（均值 20.4 字 vs 全语料 19.1 字），走**生产管线**（同一提示词、同一门禁、全新空缓存）：

```
样本        80 条 / 1,629 字（长度 3–31，中位 21）
用时        32.8 秒
请求        15 次（其中拆分重试 1 次）——前 10 个请求就覆盖了全部 80 条
通过        76/80（95%）
吞吐        146 条/分    50 字/秒
生成        1,738 token   53.0 tok/s（每条原文 20.4 字 → 生成 21.7 token）
失败        3×refused  2×unchanged  2×prompt-echo
```

53 tok/s 与手册里 4B 的 37 tok/s 相互印证（1.8B 约为 4B 的 1.4 倍速）。

**时间估算**：`323,152 / 146 条每分 = 36.9 小时`；`6,186,764 / 50 字每秒 = 34.4 小时` → **约 1.5 天**。这是"机器不停"的理论值，实际受单局 180 分钟预算、卡死重试、显存与散热影响。

## 四、质量实测：日文残留（`kana-residue.js`）

通过质量门禁 **≠** 译文干净。门禁的 `kana-only` 只在**整行都是假名**时才判死，一行里夹着没翻的人名/词它抓不到。

| 指标 | 1.8B 本次实测（76 条） | 部署现有缓存（155,320 条，主要 4B + MTool 导入） |
|---|---|---|
| 译文里残留假名（连续 ≥2 个假名字母） | **13.16%**（10 条） | **0.47%**（733 条） |
| 译文与原文完全相同 | 0.00% | 2.89% |

1.8B 残留的 13 个片段**各不相同**（不是同一个名字反复出现），既有人名也有普通词句：

```
フラン / フランの          人名
オナホヒロイン / オナホとして   普通名词整词没翻
キモオ / キモおじさま        普通名词整词没翻
ちょっとおまんこが / したらおちんぽ / びくんびくん / どびゅっ   整句、拟声词没翻
さん                    敬称
```

现有缓存残留的 245 种里，出现最多的是 `ダイスケ ×341`、`ダイスケさま ×34`、`ルル ×21`、`アメリア ×17`——**"人名保留原文"是这个管线的历史通病，不是 1.8B 独有的**；但 1.8B 把它放大到 28 倍，而且从"人名"扩散到"整词整句"。

> 注：13% 是在**单局**样本上测的（`_OreNo小屋…`，该局对白反复出现同一批角色），换局数字会浮动；但"1.8B 明显比 4B 脏"这个方向是稳的。

## 五、建议

1. **1.8B 适合"先快速铺一遍"**：1.5 天把 32 万条铺完，短条目 95% 可用，成本几乎为零。
2. **要干净成品就用 4B**：只慢 1.4 倍（2.2 天 vs 1.5 天），残留率从 13% 降到 0.5% 量级。按"成品质量/时间"这笔账，**4B 更划算**。
3. **铺完之后用"检查翻译"收尾**：它拿 `data_原版备份` 的原始日文当基准重翻、且只在结果更好时替换，正好用来把 1.8B 留下的残留挑掉。
4. **人名一致性用术语表**：在游戏目录放 `glossary.txt` 写 `ダイスケ->大辅`（或故意保留），管线会强制替换，能一次性解决 `ダイスケ ×341` 这类历史残留。
